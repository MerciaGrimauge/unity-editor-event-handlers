# 実行契約とライフサイクル

条件プロバイダーとイベントハンドラーを登録した後の動作を説明します。メソッドのシグネチャ・引数・戻り値・例外は[APIリファレンス](API_REFERENCE.md)を参照してください。

## 登録と解除

通知型は厳密な型で識別します。同名の別型や基底・派生型を同じ配送先として扱いません。各通知型の条件は1件だけ登録できます。ハンドラーは対応する条件がなくても購読でき、その条件が登録・有効化されるまで待機します。

登録数の上限は**条件登録と購読の合計100件**です。無効・待機中・登録処理中の予約も含みます。複合購読は1枠、依存する条件登録はそれぞれ1枠です。枠の予約は実装のgetterを読む前に行い、上限到達時はgetterを呼ばず拒否します。登録失敗では予約を解放し、getterの例外は呼び出し元へ伝播します。getterは軽量な処理にしてください。

ディスパッチャーは登録した実装とトークンを強参照します。トークンを手放しても登録は残ります。解除にはEditorメインスレッドで`Dispose()`を呼びます。同じトークンの再解除は無操作です。条件を解除すると、その購読は解除されず待機します。

登録の寿命はEditorドメイン内です。`InitializeOnLoad`などで必要に応じて再登録します。通知の再送や既存シーンの初期探索はありません。任意の通知を投入する公開API、実行環境を差し替える公開APIはありません。

## 判定結果の共有と配送

バッチ開始時の登録構成から配送先を決めます。新規登録は次バッチから対象です。解除・無効化は残りの配送にも反映します。依存条件が解除・無効化・別登録へ置換された場合、保存済みの結果は配送に使いません。ORで選択されなかった依存条件もこの確認の対象です。

有効な購読に必要な条件だけを評価します。同じ入力変更1件につき各条件を最大1回評価し、単一・AND・OR購読で結果を共有します。指定された入力Kindに関心がない条件は、その入力では不一致です。**バッチ全体の条件評価が終わってからハンドラーを実行**します。

ハンドラーは逐次実行します。実行順と先後関係は公開契約に含めず、登録側から希望・優先度を指定するAPIもありません。登録順・ID・管理画面の表示位置から実行順を前提にしないでください。ハンドラーは前後のハンドラーの存在・成功・対象状態を前提にせず、使用する参照を実行時に確認してください。

通知値は購読者間で共有されます。読み取り専用の型・一覧を使っても、含まれるUnity参照の状態は後で変わり得ます。入力の種類・識別子・親遷移は保存しますが、オブジェクト全体の状態を凍結しません。`BatchId`とUnity識別子は一時的な値で、永続保存に使用しません。

## ANDとOR

| 購読 | 同じ入力変更での動作 | ハンドラーへ渡す結果 |
|---|---|---|
| `Subscribe<TEvent>` | 対応する1条件が一致 | `TEvent` |
| `SubscribeAll` | 全条件が一致し、同じRootとシーンを返す | 全条件の結果を含む`CompositeEvent` |
| `SubscribeAny` | 型一覧の先頭から最初に一致した条件を選ぶ | その1条件の結果だけを含む`CompositeEvent` |

両複合モードで、すべての依存条件が登録済みかつ有効であることを要求します。未登録・手動無効・異常無効を「不一致」とみなしてORで迂回しません。

ORの短絡は保存済み結果の選択に適用します。必要な条件の評価そのものは省略しません。別入力・別バッチの一致を蓄積して結合すること、AND/ORの混在や入れ子、Rootの範囲を合成して広げることはありません。

型一覧は登録時にコピーして順序を保持します。購読後に元の配列を変更しても条件構成は変わりません。型一覧の制約と登録時の例外は[EditorEvents](api/EditorEvents.md)、結果の取得方法は[CompositeEvent](api/CompositeEvent.md)を参照してください。

## 呼び出しの期限

条件・ハンドラーの期限は**各呼び出しで独立**しています。既定値・上限は100 ms、管理ウィンドウから1〜100 msの整数で変更できます。共有のバッチ時間予算はありません。呼び出し開始時の設定をコンテキストへ保持し、登録側は期限変更・延長・再有効化を行えません。

処理の区切りで`CheckDeadline()`を呼びます。ディスパッチャーも処理が戻った後に期限を確認し、条件の不一致も確認対象です。メインスレッド上の同期呼び出しを強制停止する機構はありません。制御が戻らない無限ループも協調的な期限検査で停止できるとは扱いません。

`ConditionContext`は判定中、`HandlerContext`は実行中だけ使用します。終了済みコンテキストの期限検査・編集は拒否します。後で行う作業へ持ち越さず、非同期編集・遅延編集・モーダル表示・イベントループ再入・直接Undo操作を行わないでください。

## 終了結果と無効化

| 終了状態 | ディスパッチャーの処理 |
|---|---|
| `Succeeded` | 期限と実行後の確認を通過すれば追跡済み変更を確定 |
| `Skipped` | 追跡済み変更がなければ次へ継続。変更後のSkipは失敗扱い |
| `Failed` / `Cancelled` | 追跡済み変更を復元し、その購読を異常無効化 |
| `Unspecified` / 不正値 | 契約違反として失敗扱い |

ハンドラーの通常例外・期限超過は`Failed`、`OperationCanceledException`は`Cancelled`へ変換します。復元が成功すれば次の購読へ進めます。条件の例外・期限超過・不正な一致結果ではその条件を異常無効化し、依存する購読を待機させます。条件は読み取り専用の契約であり、条件が直接変更したUnity状態を復元する処理はありません。

確定・復元の異常、またはハンドラー実行後のRoot喪失では、原因の購読を異常無効化し、残りの購読・通知を即時打ち切ります。`Success()`を返していても、Rootが失われていれば`LastResult`を失敗へ更新します。

全体停止はメモリ上の状態で、ドメインリロードまたはEditor再起動で解除されます。原因登録の異常無効化は永続記録として残ります。再開前にConsoleとシーンを確認してください。

## 編集と復元の範囲

編集範囲は条件が指定した通常シーンのRootと子階層です。編集対象は同じシーンのGameObject/Componentで、永続アセットではない必要があります。通知にRoot外の参照が含まれても編集範囲は広がりません。

最初のコンテキスト編集でUndoグループを開始し、必要な対象とPrefabのPropertyModificationを記録します。`Modify`は指定した対象のシリアライズ可能なプロパティだけを編集します。作成・削除・親変更には専用メソッドを使い、別対象の変更は個別に記録します。[HandlerContext](api/HandlerContext.md)に対象制約と例外を記載しています。

復元はその購読の追跡済み変更に限ります。元のユーザー操作と、前の正常終了した購読の変更を保持します。階層全体のメモリ保存ではなく、直接書き込み・外部ファイル・非シリアライズ状態・コンポーネントの副作用・後から実行される処理は対象外です。Rootの直接破壊も復元を意味しません。dirty状態や既存Redo履歴が変わる場合があります。

Unity参照への直接変更を遮断するサンドボックスではありません。登録実装は公開契約に従い、第三者Componentの継続更新やライフサイクルの副作用も個別に扱ってください。

## 管理ウィンドウと設定保存

管理ウィンドウは`Tools / MerciaGrimauge / Editor Event Handlers`です。有効/無効、独立した期限、購読条件、取得できる条件ソースを確認できます。設定変更はユーザー操作用の内部管理APIで行い、登録実装には公開しません。

手動設定と異常無効化理由は、プロジェクト・登録種別・通知型・IDに対応してEditorPrefsへ保存します。同じIDの再登録・ドメインリロード・Editor再起動でも異常無効化は残ります。UIから有効化すると異常理由を解除し、手動無効化した場合はその指定を優先します。

複合購読の設定は`CompositeEvent`とハンドラーIDで識別し、モード・型一覧をキーに含めません。構成を変えて同じIDで再登録すると設定を引き継ぎます。別機能は別IDにしてください。

実装には旧SessionStateの異常理由を引き継ぐ分岐が残っています。永続記録がない場合だけ移行し、永続記録があれば優先します。現在の登録側がSessionStateへ保存する必要はありません。

## Unity入力とメモリの寿命

Unity変更通知のうち、購読に必要な種類だけを受け取ります。Play中・移行中、コンパイル・アセット更新・Playerビルド・Undo処理中は実行しません。Undo/Redoでは保留通知を破棄し、次のEditor更新まで除外します。同じ周期の独立した変更も除外される場合があります。

通知は変更の発生元の証明ではありません。他ツールやハンドラー自身の後の変更も届き得ます。シーン読み込み専用の通知、既存シーンの一括探索、常時の入力・選択監視はありません。公開Kindの一覧は[EditorChangeKind](api/EditorChangeKind.md)を参照してください。

同じ更新までに種類と全識別子が同じ入力を重複排除します。通知キューは更新後に内容をクリアし、確保容量を再利用します。キュー件数のハード上限はありません。判定結果はバッチ内だけで共有し、配送後に解放します。通知履歴として保持し続ける設計ではありません。
